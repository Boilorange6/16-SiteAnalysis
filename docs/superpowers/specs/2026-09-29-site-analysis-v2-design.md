## 1. 목표와 범위

주소 하나를 입력하면 반경 안의 입지 요소를 분석하고, 결과를 **타일 보드**로 보여주며, **모든 타일을 PPT 슬라이드로** 내보내는 앱으로 전면 재구축한다.

### 확정된 제품 결정

| 항목 | 결정 |
|---|---|
| 사용자 | 회사 내부용으로 시작. 나중에 공개할 수 있게 설계하되 공개 기능은 만들지 않는다 |
| 산출물 전달 | 회사 안에서만 사용(외부 발주처·협력사 전달 없음) |
| 데이터 범위 | 전국 |
| API 키 | 서버가 관리. 사용자별 네이버 키 입력 UI 제거 |
| 분석 단위 | 주소 하나. 후보지 비교 없음 |
| 용도 프리셋 | 없음. 분석은 하나이고 보고서에서 타일을 켜고 끈다 |
| 흐름 | 대지 지정 → 분석(보드) → 보고서 3단계 |
| UI | Alt 4 타일 보드. 분석·도판·시뮬레이션이 모두 타일 |
| 기능 범위 | sitedia 분석 전부 + 우리 고유 기능(정비사업·계획 철도·실거래·통학구역·인구) |
| 점수 | 현재 종합 점수(100점)와 S~D 등급 폐기 |
| 판단 기준 | 제안 거리 기준을 쓰고 "내부 제안 기준"으로 표시 |
| 바람 | 브라우저 탐색용. 검증 CFD는 범위 밖 |
| 3D 파일 | GLB·3DM 먼저, SKP는 나중 |
| 개발·운영 위치 | 서버 없이 로컬 PC에서 먼저 구현. 배포 서버는 나중에 고른다 |
| 저장소 | 같은 레포에서 기존 앱과 병행 개발 |

### 범위 밖

후보지 비교, 용도 프리셋, 종합 점수, 검증 CFD, 공개 서비스용 기능(가입·과금·공유 링크), 서버 동기화·협업, 배포 서버 선정(마지막 단계에서 따로 결정).

## 2. 제품 개념 (①)

- **타일**은 보드의 최소 단위다. 종류는 넷이다: 분석, 도판, 시뮬레이션, 스택.
- 보드에서 체크한 타일이 **보드 순서대로** 슬라이드가 된다.
- 도판 타일은 뒤집으면 구성비가 보인다. 시뮬레이션 타일은 타일 안에서 재생되고, 펼치면 상세 화면이 된다.
- 조판은 보드를 한 장에 배치해 인쇄하는 기능이고, 레이어 스택은 선택한 도판을 겹친 타일이다.

## 3. 데이터 구조 (②)

### 3.1 원칙

1. **분석 요청은 로컬 데이터만 읽는다.** 전국 데이터를 분석 요청과 무관하게 미리 적재한다.
2. 분석 중 외부 호출은 셋만 남기고 따로 집계한다: 주소 검색(1~2회), 대상 필지 최신 정보(선택, 1~3회), 허용된 WMTS 배경지도·항공사진 타일.
3. 원천 장애가 나도 자동으로 외부 재수집하지 않는다. 마지막 정상본과 "미확인" 상태를 보여준다.
4. 원천 장애를 정상 0건으로 표시하지 않는다.
5. **대상 필지 최신 조회는 기본 분석과 분리한다.** 분석에 반영할 때는 응답·기준일·취득 시각을 불변 스냅샷으로 저장하고, 응답 해시를 결과 의존성과 캐시 키에 넣는다.

현재는 3km 분석 한 번에 외부 호출이 60~300회다(api-audit §1). 목표는 **구조화 분석 데이터 조회**(도판·분석 타일의 벡터·속성·수치)에 필요한 외부 호출 0회다. 2번의 호출은 이 목표에서 제외하고 별도로 센다.

### 3.2 저장 구조

```text
app.sqlite                  사용자·프로젝트·분석 실행·타일 결과 (교체 대상 아님)

data/<version>/
  core.sqlite               건물·필지·용도지역·행정경계
  reference.sqlite          학교·학구·상가·공원·버스·인구 격자·구역·도시계획시설·OSM 도로
  market.sqlite             실거래·정비사업·청약·입주예정·계획 철도
  buildings.sqlite          건물 도형·높이 (GIS건물통합정보)
  parcels.sqlite            연속지적 필지 도형
  *.pmtiles                 화면 표시용 벡터 타일
  terrain.sqlite            지형 DEM (SRTM 1″ HGT 행 BLOB)
  weather.sqlite            기상 대표 자료 (ASOS 풍향 16방위 × 풍속 5구간 빈도)
data/manifest.json          현재 쓰는 파일 목록·해시·버전·출처 (포인터)
```

- 저장소는 **SQLite + R*Tree**. SpatiaLite·PostGIS는 쓰지 않는다. 공간 조인이 실제 병목으로 측정되면 그때 검토한다.
- 현재 한 DB에 섞여 있는 사용자 데이터와 공공데이터 캐시를 분리한다(`src/lib/server/database.ts`).
- PMTiles는 표시 전용이다. 정밀 분석·DXF는 SQLite 원본 도형을 쓴다.
- 필지·건물 파일이 너무 커지면 그때 시도 단위로 나눈다. 처음부터 나누지 않는다.

### 3.3 핵심 테이블

| 테이블 | 목적 |
|---|---|
| `source_release` | 원천 배포본·기준일·수집일·해시·라이선스·커버리지 |
| `ingest_run` | 적재 실행별 이력·건수·상태 |
| `feature` | 모든 공간 객체(건물·필지·학교·학구·도로·구역). `kind`로 구분 |
| `building_fact` | 건물 속성(높이와 높이 근거, 층수, 용도, 사용승인일, 면적) |
| `feature_link` | 객체 간 다대다 연결과 연결 근거·신뢰도(건물↔필지, 단지↔동, 학교↔학구) |
| `observation` | 시점별 수치(공시지가·인구·기상 집계) |
| `property_transaction` | 유형별 실거래(매매·전월세, 해제·정정 포함) |
| `development_event` | 정비사업·계획 철도·청약·입주예정의 단계와 일정 |
| `analysis_run` (app) | 분석 조건과 사용한 manifest 해시 |
| `tile_result` (app) | 모든 타일의 결과. 화면과 PPT가 함께 쓴다(§5.2) |

컬럼 초안은 data-architecture-astra §4. 규칙:

- PNU·법정동 코드는 **문자열**이다. `Number`로 바꾸지 않는다.
- 건물 도형, 대장 표제부, 총괄표제부, 단지는 서로 다른 객체이며 `feature_link`로 연결한다. 이름 유사도는 최후 수단이다.
- 모르는 값은 `NULL`이다. 0이나 오늘 날짜로 채우지 않는다. `value_status`는 `observed / estimated / suppressed / missing / not_applicable`.
- 거리·면적은 미터 단위 국내 투영좌표계로 계산한다. Web Mercator 면적으로 구성비를 내지 않는다.
- R*Tree로 후보를 추린 뒤 실제 교차·포함·거리 판정을 한다. 대표점이 반경 밖이라는 이유로 교차 필지를 빠뜨리지 않는다.
- 반경과 교차하는 **모든** 법정동·시군구를 로컬 경계로 구한다(현재 역지오코딩 21회를 대체, 시군구 경계 누락 해소).

### 3.4 데이터 교체

1. 새 파일을 별도 경로에서 완성한다.
2. 무결성·R*Tree·행수·공간 범위·참조 관계·해시를 검사한다.
3. 후보 manifest로 고정 지점 기대치를 검사한다(§3.5). 통과해야 게시한다.
4. `manifest.json`을 원자적으로 바꾼다. 진행 중 분석은 이전 파일을 계속 쓰고, 새 분석부터 새 버전을 쓴다. 게시 뒤 현재 manifest가 검사한 후보를 가리키는지 확인하고, 아니면 직전 manifest로 되돌린다.
5. 검사 실패 시 이전 정상본이 그대로 남는다.
6. **저장된 프로젝트가 참조하는 manifest·데이터 파일·결과 산출물은 참조가 남아 있는 동안 지우지 않는다.** 다시 열기는 저장된 결과를 그대로 복원하고, 최신 데이터로 다시 분석하는 것은 별도 실행으로 만든다.

### 3.5 적재

| 작업 | 위치 |
|---|---|
| 전국 파일 가공(GIS건물통합정보, 연속지적도, 용도지역, 대장, OSM PBF, SGIS 격자, DEM, PMTiles) | 로컬 PC(RAM 64GB, 16스레드, D: 여유 326GB) |
| 가벼운 API 수집(RTMS, 청약, 정비사업, K-APT) | 로컬 PC 예약 작업. 배포 후에는 서버 크론 |
| 로그인이 필요한 원천(정비구역 SHP, 학구도) | 사람이 받은 원본을 같은 검증 경로에 넣는다 |

단계: `취득 → 원본 검증 → 정규화 → 연결 → 품질 검사 → 산출물 생성 → 게시 → 고정 지점 확인`.

품질 검사(모든 원천 공통):

- 응답에 행이 있는데 파싱 결과가 0건이면 실패.
- 전국 합계가 30% 넘게 줄면 거부(현행 유지).
- 특정 시도·유형이 통째로 사라지면 게시 보류.
- 좌표·높이·용도·준공일 채움률이 급락하면 경고·보류.
- 페이지 상한 도달이나 `totalCount` 불일치는 불완전 수집으로 처리.
- 고정 지점 기대치를 게시 전에 확인한다. 기대치는 P0에서 §6.1 검수 지역의 첫 적재 결과를 **원천 총건수와 독립 확인 표본에 대조한 뒤** 승인해 고정한다. 첫 적재의 누락을 그대로 정상으로 삼지 않는다(기존 예: 다산동 공동주택 56건).

실거래는 분석 요청과 무관하게 **전국 시군구 × 지원 유형 × 보관 월**을 적재하고, 분석할 때는 반경과 교차하는 모든 시군구 자료를 조회한다. 최초 적재는 24개월이다. 최근 2개월은 매일, 3~12개월은 매주 다시 받는다. 13개월 이상 보관 중인 월도 순환해서 다시 받고(늦은 신고·정정·해제 반영), 월마다 마지막 완전 수집일을 기록한다. 고유 거래 ID가 없는 서비스는 해시 중복 제거 대신 월별 원본 집합을 통째로 교체한다.

## 4. 분석 기능 (③)

### 4.1 판단 원칙

- 좋음·보통·주의는 **거리 지표에만** 쓰고, 기준을 화면과 슬라이드에 함께 적는다. 모두 직선거리이며 "내부 제안 기준"으로 표시한다.

| 대상 | 좋음 | 보통 | 주의 |
|---|---|---|---|
| 운영 철도역(출입구) | ≤ 500m | ≤ 1,000m | > 1,000m |
| 버스정류장 | ≤ 300m | ≤ 600m | > 600m |
| 공원 입구 | ≤ 500m | ≤ 1,000m | > 1,000m |
| 배정 초등학교(학구 확인 시) | ≤ 500m | ≤ 1,000m | > 1,000m |

- 공급·가격·인구·개발은 좋다·나쁘다로 바꾸지 않고 사실을 말한다.
- 판단 문장은 **사실 → 의미 → 확인할 것** 순서다. 핵심 입력이 없으면 판단을 보류한다.
- 직선거리를 "도보 n분"으로 환산하지 않는다. 보행 시간은 OSM 보행망 라우팅을 도입한 뒤 추가한다(P4 이후).
- 조회 반경 밖에 대해서는 "반경 내 확인되지 않음"이라고 쓴다. "없음"이라고 쓰지 않는다.

### 4.2 분석 타일 12종

지표 정의·계산식·미확인 처리는 tile-catalog-astra §2.

| ID | 타일 | 핵심 지표 | v1 |
|---|---|---|---|
| A01 | 입지·교통 | 최근접 역 출입구·버스정류장 거리, 반경 내 역·노선·정류장 수 | ✔ |

### 4.3 도판 27종

범례 구간·채움률·구성비 분모는 tile-catalog-astra §4. 공통 규칙:

- 채움률은 넷으로 나눈다: `F속성`, `F면적`, `F시간`, `F연결`. 분자·분모·기준일을 함께 보인다. 원천의 지역 커버리지는 별도로 표시한다.

- 모양은 둥근 사각 + 한글 캡션이다(sitedia의 원형 + 영문 캡션을 따르지 않는다).

### 4.4 시뮬레이션 타일

네 타일 모두 같은 장면을 쓴다: 대상 영역 + 주변 영향 영역 + 건물 형상·높이 + 지형 + 좌표 원점 + 데이터 버전. S01·S02(와 이를 재사용하는 D21)는 엔진(Node)에서 계산해 타일 결과로 캐시한다. S03·S04의 브라우저(Web Worker / WebGPU) 계산 여부는 S03 구현 때 정한다.

| ID | 타일 | 결과 | 슬라이드 컷 | 한계 문구 요지 |
|---|---|---|---|---|
| S01 | 3D 매스 | 건물 수, 높이 확보율, 추정 높이 동수, 높이 중앙값·최댓값 | 1컷 | 공개 도형과 확보 높이로 만든 매스. 높이 미상 건물은 바닥 모양만 |
| S02 | 일조·그림자 | 시각별 음영 면적률, 일조시간 중앙값, 지정 시간 이상 확보율 | 1컷 / 09·12·15 3컷 (계절 4컷은 P4) | 기하학적 추정. 날씨·법적 일조 판정 아님 |
| S03 | 바람(탐색용) | 상대풍속 U/Uref 분포·구간 면적률 | 1컷(계절 입력이 정의되면 4컷) | 탐색용 모형. 보행 안전·인허가·검증 CFD 아님 |
| S04 | 열쾌적 UTCI | UTCI 중앙값·상위 분위, 양지·그늘 차이, 입력 범위 밖 면적률 | 1컷 / 3컷 / 4컷 | 대표 기상과 단순화한 복사·바람 입력의 근사값 |

- 일조는 10분 간격으로 계산하고, 표시 반경보다 넓은 주변 영향 영역을 포함한다. D21 일조시간 도판은 S02 결과를 재사용한다. 계산 시간창은 09~15시(최대 6시간)라서 6시간을 넘는 구간은 비며, 타일에 "최대 6시간"을 표시한다.
- UTCI 풍속은 10m 기준이며 적용 범위는 0.5~17m/s다. 범위 밖 값을 조용히 자르지 않는다.
- S04는 명시적 평균복사온도 모델과 대표 기상 풍속으로 먼저 구현한다. S03 결과는 기준 높이·모델 의미가 호환된다고 검증한 경우에만 S04에 연결한다. 복사 모델이 없으면 공간별 UTCI 지도를 만들지 않는다.
- GPU를 지원하지 않거나 계산을 취소·실패하면 그 상태를 남긴다. 부분 결과를 완료로 내보내지 않는다.

### 4.6 현재 앱에서 가져가는 것과 버리는 것

- **가져감:** 거리·고유 개수·면적 계산, 원천 실패·stale 처리, 출처·신뢰 표시, 정비사업 경계·단계·기준일, 계획 철도 레지스트리(증거 URL·재검토일), 적재 급감 거부, 편집 가능한 PPT 텍스트·표.
- **버림:** `computeAnalysisScores`와 점수 기반 서술, S~D 등급, 직선거리 도보 n분, 면적으로 만든 가상 원형 공원 거리, 고정 장수 PPT와 빈 주거 상세 페이지, 사용자별 네이버 키 입력.
- 기존 앱은 v2가 P1을 통과할 때까지 그대로 둔다. v2는 **별도 DB 경로·접근 모듈·스키마 버전**으로 만들고, 기존 `database.ts`·`dataset-store.ts`(현재 `ingest_run`은 데이터셋별 마지막 상태 구조)와 기존 API·사용자 키 동작은 건드리지 않는다. 기존 저장 프로젝트를 v2로 옮기는 일은 별도 검증 절차로 한다.

- 도판의 출력 면(앞면/뒷면/둘 다)은 타일마다 **명시적으로 저장**한다. 화면에서 잠깐 뒤집어 본 상태는 PPT에 반영하지 않는다.
- 긴 목록은 자동으로 여러 장을 만들지 않는다. 펼친 목록에서 "상세 페이지 추가"를 눌러야 붙고, 기본 장에는 표시 건수/전체 건수를 적는다.
- 3D 파일은 PPT에 넣지 않고 부록 링크로 붙인다.

### 5.2 `tile_result` 계약

모든 타일의 결과는 다음을 담는다. PPT·PNG·DXF·GLB는 모두 이 결과에서 만든다. **내보내는 동안 새 데이터를 조회하지 않는다.**

### 6.2 v1 완료 기준

- 시군구 경계에 걸친 반경에서도 실거래·학교·사업이 빠지지 않는다.
- 같은 입력과 manifest로 다시 계산한 화면·구성비·PPT 수치가 일치한다.
- 원천 실패, 비공개, 미확인, 실제 0건이 구별되어 보인다.
- 층수와 미터 높이, 직선거리와 보행거리, 계획 시설과 운영 시설이 섞이지 않는다.
- 모든 슬라이드에 출처·자료 기준일·미확인이 보인다.
- 타일 추가·제거·순서·출력 면·저장 후 다시 열기가 PPT와 일치한다.
- DXF·GLB를 실제 프로그램(AutoCAD 호환, Rhino/Blender)에서 열어 단위·위치·축을 확인한다.
- 8곳 검수 주소 모두에서 보고서가 생성된다.
- **8곳 검수는 전국 커버리지 검사를 대신하지 않는다.** 원천별로 전국 수집 대상 대비 확보·누락 현황(시도·시군구 단위)을 검증한다.
- **건물·필지·토지이용 기반이 전국으로 확보되지 않으면 v1 완료를 선언하지 않는다.**
- 권리·도형 문제로 v1에서 미제공을 허용하는 항목은 다음뿐이다: D01 항공사진, D10 수목, D26 통학구역, A02의 배정 학교 부분, D11·D12(파일 권리 미해결 시). 이 항목은 타일에 미제공 사유를 표시한다.
