# v2 P1b-1 — 분석 엔진 첫 판 (적재된 데이터로 계산 가능한 타일)

**목표:** 주소(지번)와 반경을 받으면 게시된 데이터(`.cache/v2/data`의 현재 manifest)로 타일 결과(`TileResult`)를 계산해 저장하고, `/site/v2` 보드가 예시 대신 실제 결과를 보여 준다.

## 타일 계산 규칙 (공통: 거리는 중심점→대상 직선 m, 정수 반올림, `distanceM` 사용. 도보 시간 없음)

**A01** 지표: `nearest_rail_m`(missing), `rail_stations`(missing), `nearest_bus_m`(observed; 반경 내 없으면 missing + "반경 내 정류장 없음"), `bus_stops`(observed, 0 가능). 등급: 버스 거리만 300/600 기준(`criteria`="내부 제안 기준: 버스정류장 직선 300m 이하 좋음 · 600m 이하 보통 · 초과 주의"). 문장 예: "최근접 정류장 직선 210m → 버스 접근은 가까운 편 → 철도·실제 보행 경로는 확인 필요". 노선 수는 미적재 → 지표 `bus_routes` missing.

**A03** 업종군 고정 매핑(`categoryCode`/`majorCategory` 기반, 매핑표를 코드에 두고 테스트): 식료품, 의료·약국, 음식·카페, 생활서비스, 기타. 지표: 군별 개수, 기초 4군(식료품·의원·약국·생활서비스) 확인 수 `basic_groups`(0~4), 군별 최근접 거리, `store_density` = 개수÷반경 원 면적(㎢). 등급 없음. 문장: "기초 생활시설 4군 중 n군 확인 → 반경 안에서 일상 시설 접근 가능 → 미확인 군(○○) 현장 확인".

**A04** 지표: `parks`(개수), `nearest_park_point_m`(대표점 거리, 입구 아님을 label에 명시 "공원 대표점까지"), `park_area_sum_m2`(원천 `areaM2` 합, **반경 교차 면적 아님** — label에 명시 "반경 내 공원 원천 면적 합"), `park_area_in_radius_m2`(missing, 경계 미적재). 등급 없음(입구 미확인). source as_of null → "기준일 미확인".

**A05** 대상: `housing_complex` 중 `mainUse`="공동주택" → 아파트 단지(recap), 그 외 → 기타 주거 건물, `officetel` → 오피스텔. `title-housing:*` 속성은 코드에서 확인해 같은 규칙 적용. 지표: 유형별 개수, `households`(households 있으면 사용, 없으면 units — 어느 것을 썼는지 formulaVersion/label에 기록, 둘 다 없으면 합계 제외하고 `households_unknown_complexes` 지표로 병기), `officetel_units`, `median_approval_year`(approvalDate 있는 대상만, numerator=확인 수, denominator=전체), `aged_share_pct`(분석일 기준 30년 이상 ÷ 준공일 확인, status estimated), `parking_per_household`(둘 다 있는 단지만, 없으면 missing). 등급 없음. limitation: 지역 불완전(coverage), 위치 미확인(coverage에 있으면 건수).

**A06** `planned_supply`를 `source`별로 분리: `applyhome_units`, `move_in_units`, 각 사업 수, 기간별(분석일 기준 0~12개월, 13~24개월, 일정 미확인) 원천별 세대수. 합계 지표는 만들지 않고 limitation `partial` note "청약홈·입주예정 중복 가능 · 합계 보류". `development_event`로 사업 연결이 가능하면 중복 제거를 시도하지 말고 이번엔 연결 가능 여부만 `formulaVersion`에 기록(다음 단계). 월 단위 일정에 임의 일자 금지. 등급 없음.

**모든 타일:** `provenance.sources`에 실제 사용 원천의 `sourceId`·`releaseId`·`sourceAsOf`·`fetchedAt`. `conditions`는 context에서 한 번 만든 값을 공유. `engineVersion` = `"v2-p1b-1"`. 결과는 반드시 `parseTileResult` 통과.

## 작업 순서 (TDD)

1. 픽스처 헬퍼(작은 core/reference/market sqlite를 임시 디렉터리에 만들고 manifest 게시) — 기존 `test-v2-analysis-skeleton.mjs` 방식 재사용.
2. `site.ts` + 테스트(정상·파싱 실패·모호·점 없음·좌표 입력).
3. `context.ts`·`coverage.ts` + 테스트(교차 시도 계산, as_of null 처리, 커버리지 미기록 시 unknown limitation).
4. 타일 5종 + not-provided + 테스트(각 규칙: 0건은 observed 0, 미적재는 missing, A01 등급 경계값 300/600, A04 등급 없음, A05 유형 분리·세대 기준 기록·30년 경계, A06 합계 없음·기간 버킷·일정 미확인, 문자열에 `/도보|\d\s*분|종합/` 없음).
5. `run.ts` + 테스트(캐시 재사용: 같은 입력 두 번 → 두 번째는 계산 안 함, manifest 바뀌면 재계산).
6. API 라우트 + 테스트(인증 없으면 401, 잘못된 반경 400, 정상 200 형태). 라우트 핸들러를 직접 import해 `NextRequest`로 호출하거나, 로직을 순수 함수로 빼서 테스트.
7. 화면 연결(주소 입력줄·반경·분석·오류 안내·`?analysis=`). 예시 모드 유지.
8. 실제 데이터 검수: `npm run v2:review` — 8곳 모두 오류 없이 결과, 각 1초 이내 목표(측정값 기록), 표를 `docs/superpowers/a0/2026-09-30-p1b-review.md`로 저장. 다산·복정의 A05 과소 의심은 수치 그대로 기록(고치지 말 것).
9. 검증: `npm run test:v2`, `npm run lint`, `npm run build`. Playwright로 로그인 후 `/site/v2`에서 검수 주소 1곳(지번) 분석 → 타일이 실제 값으로 바뀌는지 캡처(`docs/design/p1b/`). 로그인 계정이 없으면 캡처 단계는 건너뛰고 보고.

## 규칙

- 데이터 파일은 읽기 전용(`openDataFile`). `.cache/v2/data`에 쓰지 않는다. 다른 에이전트가 새 버전을 게시할 수 있으므로 분석마다 manifest를 읽는다.
- v1 코드 수정 금지(`requireAuth` import만 허용).
- 파일 수정은 Edit/Write 도구만. 작은 커밋, 한국어 `feat(v2-engine): …`. push 금지.
