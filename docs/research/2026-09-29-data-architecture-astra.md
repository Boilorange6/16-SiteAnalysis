**16-SiteAnalysis 재구축 ② 데이터 구조 독립 설계안**  
조사 기준: 2026-09-29

지정된 API 감사·sitedia 벤치마크 문서와 현재 서버·API·배포 코드를 읽고 설계했다. Claude의 별도 재구축 설계안은 참조하지 않았다. 파일 수정·생성·설치·커밋은 수행하지 않았다.

표기는 **[확인] 공식 자료 또는 현재 코드에서 확인**, **[추정] 용량·성능 예상 및 운영 제안**, **미확인: 이번 조사에서 확정하지 못함**이다. 운영 서버의 현재 자원 사용량과 전국 원본의 실제 다운로드 크기는 측정하지 않았다.

**1. 요약 권고**

1. 전국 데이터를 미리 적재하고, 분석 요청은 **버전이 고정된 로컬 데이터 묶음**을 읽도록 한다.
2. 저장소는 **SQLite+R*Tree를 중심**으로 하되, 사용자 DB와 교체 가능한 공공데이터 DB를 분리한다.
3. PMTiles는 화면 표시용, GeoParquet는 가공·보관용, DEM은 COG로 사용한다. 초기 PostGIS·SpatiaLite 도입은 보류한다.
4. 주소 검색·좌표 변환과 항공영상 취득만 기본 실시간 경로에 남긴다. 영상까지 포함한 외부 호출을 “0회”라고 표현하지 않는다.
5. **PNU 하나로 건물·대장·단지를 모두 연결하지 않는다.** 객체 식별자와 다대다 연결, 연결 근거를 별도로 보관한다.
6. 분석·도판·3D·시뮬레이션·PPT는 동일한 입력·데이터 버전·계산 결과를 공유한다.
7. 대용량 전국 가공은 로컬 PC, 소규모 일일 적재는 Lightsail에서 수행한다.
8. 바람 CFD는 웹 서버 밖에서 계산한다. 브라우저 간이 시뮬레이션과 검증된 3D CFD의 품질을 구별한다.
9. 전국 운영은 **8GB RAM급 서버를 우선 검토**하되, 디스크는 전국 샘플 적재 후 결정한다.
10. 가장 먼저 해결할 문제는 **전국 SHP의 이용권한, 학구도 도형 확보, 건물 높이 품질, SKP 생성 경로**다.

**2. 데이터 계층과 요청 경로**

**현재 구조에서 계승할 것과 바꿀 것**

[확인] 현재 SQLite에는 사용자·세션·저장 프로젝트와 공공데이터 캐시가 함께 들어 있다. 따라서 현재 DB 전체를 전국 데이터 파일로 교체하면 사용자 데이터까지 영향을 받는다. [database.ts](/D:/V-coding/16-SiteAnalysis/src/lib/server/database.ts:29)

[확인] 기존 적재 저장소에는 staging, 30% 초과 급감 거부, 트랜잭션 교체가 있다. 다만 공간 인덱스는 `(lat, lng)` 일반 인덱스이며 R*Tree가 아니다. 적재 이력도 실행별 이력이 아닌 데이터셋별 마지막 상태다. 이 원칙은 계승하되 전국 규모에 맞게 확장한다. [dataset-store.ts](/D:/V-coding/16-SiteAnalysis/src/lib/server/dataset-store.ts:62)

[확인] 제거해야 할 요청 시 외부 수집이 남아 있다.

- 공원: 전체 페이지를 요청 중 수집한다. [park-search.ts](/D:/V-coding/16-SiteAnalysis/src/lib/server/park-search.ts:209)
- 청약홈: 적재본이 7일을 넘으면 실시간 경로로 돌아간다. [planned-residential-search.ts](/D:/V-coding/16-SiteAnalysis/src/lib/server/planned-residential-search.ts:612)
- 실거래: 중심 시군구만 조회하며 월별 페이지 상한이 있다. [rtms-trades.ts](/D:/V-coding/16-SiteAnalysis/src/lib/server/rtms-trades.ts:447)

| 전국 기준데이터 | 건물·필지·용도지역·행정경계·학교·학구·상가·교통·공원·인구·DEM | 로컬 조회 |
| 시점별 사실 | 실거래·공시지가·정비사업 단계·청약·입주예정·기상 통계 | 로컬 조회 |
| 분석 결과 | 반경 추출, 집계, 구성비, 그림자·바람·UTCI 결과 | 계산하거나 결과 캐시 조회 |

주소가 확정되면 **원·선택 필지·사용자 구역을 하나의 분석 영역으로 정규화**한다. 이후 반경과 교차하는 모든 법정동·시군구를 로컬에서 구한다. SGIS의 행정동·집계구 경계를 법정동 경계로 대체해서는 안 된다.

실시간 외부 호출은 다음처럼 제한한다.

| 항목 | 정상 요청의 외부 호출 목표 | 비고 |
|---|---:|---|
| 주소 검색·좌표 확정 | 1~2회 [추정] | 입력 후보 검색 횟수는 별도 집계 |
| 27종 도판의 구조화 데이터 조회 | **0회** | 필요한 전국 데이터가 적재된 상태 |
| 일조·바람·UTCI 입력 확보 | 0회 | 건물·지형·기상은 로컬 자료 |
| 항공영상 | 콜드 시 수십 회 [추정] | 화면 크기·줌·영상 레이어 수에 따라 변동 |
| 선택 필지의 최신 정보 재조회 | 선택적으로 1~3회 [추정] | 기본 분석을 막지 않는 별도 동작 |
| 자료 누락·배치 실패 | 자동 외부 재수집하지 않음 | 마지막 정상본과 미확인 상태 제공 |

영상은 예를 들어 256px 타일로 2,048px 정사각 이미지를 만들 경우 정렬 상태에 따라 약 64~81장이 필요하다. 이는 **타일 규격을 가정한 계산**이며 VWorld의 현행 서비스 규격·허용량은 별도로 확정해야 한다. 여러 타일에서 같은 항공영상을 재사용한다.

**성능 목표 [추정]**

측정 조건은 전국 자료 적재 완료, 분석 결과 캐시 없음, 기본 반경 800m, 데스크톱, 동시 분석 2건이다.

| 완료 지점 | 목표 |
|---|---:|
| 분석 접수·자료 버전 확정 | 0.5초 이내 |
| 기본 도형·집계 첫 응답 | 1~3초 |
| 항공영상·시뮬레이션을 제외한 도판 표시 | p95 8초 이내 |
| 항공영상 포함 기본 보드 | p95 15초 이내 |
| 3km 고밀도 지역 기본 보드 | p95 20초 이내 |
| 일조·바람·UTCI | 별도 비동기 완료 기준 적용 |

여기서 콜드는 **결과 캐시 미스**다. 서버 재시작 직후 OS 파일 캐시까지 비어 있는 경우는 따로 측정한다. 전국 초기 다운로드·적재 시간은 사용자 분석 응답 시간에 포함시키지 않는다.

**중요한 선행 조건:** 대량 취득·가공 권한이 없는 데이터까지 로컬 적재 가능하다고 가정하지 않는다. 해당 권한을 확보하기 전에는 일부 도판에 실시간 조회나 미확인 상태가 남으며, 위의 외부 호출 0회 목표는 미달 상태다.

**3. 소스 표**

전국 크기는 별도 표시가 없으면 모두 **[추정] 용량 계획 범위**다. `원본 → 가공`에서 원본은 압축 배포본 또는 압축 원본 응답의 합, 가공은 필요한 필드·공간 인덱스를 포함한 운영 자료다. 전체 이력·복제본·영상 캐시는 제외한다.

제공자가 표기한 갱신 주기와 우리 적재 주기를 구별했다. 데이터 페이지의 수정일은 실제 관측·조사 기준일을 뜻하지 않는다.

**4. 저장 구조**

**권고: SQLite 중심, 데이터 교체 단위에 따른 소수의 파일**

```text
영속 사용자 영역
  app.sqlite                 사용자·프로젝트·분석 실행·타일 결과·작업 상태

버전이 고정된 데이터 영역
  core-<version>.sqlite      건물·필지·토지이용·행정경계
  reference-<version>.sqlite 학교·학구·상가·공원·격자 통계
  market-<version>.sqlite    실거래·개발사업·공급 정보
  osm-<version>.sqlite       OSM 도형·속성 및 파생자료

파일 산출물
  <hash>.pmtiles             지도 표시용 벡터 타일
  <hash>.tif                 지형 COG
  <hash>.epw                기상 입력
  분석별 SVG·PNG·GLB·3DM·SKP·DXF

  데이터 파일 경로·해시·버전·출처·호환 스키마를 묶은 목록
```

처음부터 시군구별 수백 개 DB로 분할하지 않는다. 전국 필지 파일이 실제로 너무 커지거나 갱신 부담이 확인되면 **필지·건물만 시도 단위로 분할**한다. 경계에 걸친 분석은 관련 파일 전체를 조회한다.

| 선택지 | 역할·판정 |
|---|---|
| SQLite+R*Tree | 기본 채택. 로컬 공간 후보 검색·속성 조인·집계에 적합 |
| SpatiaLite | 초기 미채택. 서버별 네이티브 확장 배포 부담보다 이득이 큰지 먼저 측정 |
| PostGIS | 복잡한 공간 조인이 실제 병목이 되거나 동시 사용·갱신 요구가 커질 때 도입 |
| PMTiles | 화면 표시용. 단순화·클리핑될 수 있으므로 정밀 분석·DXF 원본으로 사용하지 않음 |
| FlatGeobuf | 대용량 벡터 교환·부분 읽기가 필요할 때 선택. 초기 필수 저장소로 늘리지 않음 |
| GeoParquet | 로컬 가공·중간 산출물·보관용. 브라우저 요청 DB로 쓰지 않음 |
| COG | DEM의 범위 읽기·해상도별 조회용 |

PMTiles는 필요한 구간을 HTTP Range로 읽을 수 있는 단일 아카이브다. 초기에는 Lightsail의 정적 파일 제공으로 충분하며, Nginx의 Range 응답과 캐시 헤더를 확인한다. [PMTiles 문서](https://docs.protomaps.com/pmtiles/)

**식별자·시간·품질 규칙**

- PNU와 법정동 코드는 문자열이다. 특히 PNU를 JavaScript `Number`로 변환하지 않는다.
- 건물 도형, 건축물대장 표제부, 총괄표제부, 아파트 단지는 서로 다른 객체다.
- 건물 하나가 여러 필지에 걸치거나 필지 하나에 여러 동이 있을 수 있으므로 다대다 관계를 보존한다.
- 건축HUB의 PK 변경도 공급자 식별자 전환 문제로 취급한다. 공식 API에 PK 전환 규칙 안내가 있다. [건축HUB API](https://www.data.go.kr/data/15134735/openapi.do)
- `source_as_of`, `published_at`, `fetched_at`, `effective_date`를 구별한다.
- 미상 높이·좌표·기준일은 `NULL`이다. 0이나 현재 날짜로 대체하지 않는다.
- `value_status`는 최소한 `observed / estimated / suppressed / missing / not_applicable`을 구분한다.
- 출처가 다른 높이·층수·용도·준공일은 필드별 출처와 선택 근거를 남긴다.

**공간 인덱스와 좌표**

전국 거리·면적 계산용 좌표계는 미터 단위의 국내 투영좌표계로 통일하고, 원본 CRS와 변환 이력을 보존한다. 웹 표시에는 WGS84/Web Mercator를 사용하되 Web Mercator 면적으로 구성비를 계산하지 않는다.

```sql
CREATE VIRTUAL TABLE feature_rtree USING rtree(
  feature_id,
  min_x, max_x,
  min_y, max_y
);
```

R*Tree는 bbox 후보만 좁힌다. 이후 원·폴리곤과의 실제 교차, 점 포함, 거리 판정을 수행한다. 필지 대표점이 반경 밖이라는 이유로 교차 필지를 누락하지 않는다.

SQLite R*Tree는 빌드 설정에 따라 활성화 여부가 달라질 수 있다. 현재 설치 바이너리에 대해서는 구현 단계에서 확인해야 한다. [SQLite R*Tree 문서](https://www.sqlite.org/rtree.html)

결과 캐시는 `분석 영역＋manifest_hash＋엔진 버전＋분석 조건`으로 구분한다. 좌표 반올림 캐시는 후보 도형 재사용에만 쓰고, 최종 집계는 실제 분석 영역으로 다시 계산한다.

**원자적 교체**

1. 새 파일을 기존 서비스와 분리된 staging 경로에서 완성한다.
2. DB 무결성·R*Tree·행수·공간 범위·참조 관계·해시를 검사한다.
3. WAL이 남지 않은 닫힌 읽기 전용 데이터 파일을 게시한다.
4. 모든 필요한 파일이 준비된 뒤 manifest 포인터 하나를 같은 파일시스템에서 원자적으로 교체한다.
5. 진행 중 분석은 이전 manifest와 열린 파일을 계속 사용한다. 새 분석부터 새 버전을 사용한다.
6. 이전 파일은 사용 중인 요청이 끝난 뒤 보존 정책에 따라 정리한다.

`app.sqlite`는 교체 대상이 아니다. WAL 사용 중인 DB를 파일 복사 하나로 백업하지 않고 SQLite의 일관된 백업 절차를 사용한다. 앱 버전 롤백과 데이터 버전 롤백도 분리한다.

**5. 적재 파이프라인**

**실행 위치**

| 작업 | 권고 위치 | 이유 |
|---|---|---|
| 전국 SHP·PBF·대장·격자 변환 | 로컬 PC | 대량 압축 해제·조인·도형 정리는 웹 서비스와 분리 |
| 초기 전국 RTMS 과거 자료 수집 | 로컬 PC 또는 일회성 워커 | 긴 수집 시간과 재시작 관리 |
| 청약·정비사업 API·최근 RTMS | Lightsail의 별도 배치 프로세스 | 적은 변경량, 상시 운영 용이 |
| PMTiles·DEM 파생본 생성 | 로컬 PC | CPU·메모리 사용량 제한 |
| 정비구역·학구도 수동 취득 | 운영자가 받은 원본을 동일 검증 경로에 투입 | 로그인·신청 절차를 우회하지 않음 |

상시 별도 워커 서버는 초기 필수가 아니다. 로컬 PC가 꺼져 있는 경우에도 마지막 정상 데이터로 서비스가 유지되도록 한다.

[확인] 현재 `ingest-cron.sh`는 `current` 릴리스, 공유 환경설정, 작업별 `flock`, 로그를 사용한다. 이 구조를 확장하면 된다. 다만 스크립트의 직접 분기는 `planned`, `ledger` 두 종류이며, 운영 크론 3종의 실제 설치 상태는 이번 조사에서 재검증하지 않았다. [ingest-cron.sh](/D:/V-coding/16-SiteAnalysis/deploy/ingest-cron.sh:19)

**단계**

`취득 → 원본 검증 → 정규화 → 공간·식별자 연결 → 품질 검사 → 산출물 생성 → 게시 → 서비스 확인`

각 단계는 `run_id`와 입력 해시를 가지며 중간 실패 후 재개할 수 있게 한다.

- **취득:** 페이지 끝까지 수집하고 기대 페이지·행수와 비교한다. HTML 오류 페이지나 인증 실패를 데이터로 저장하지 않는다.
- **정규화:** 인코딩, 좌표계, 단위, 날짜 정밀도, 취소·삭제 상태를 변환한다.
- **연결:** PNU·공식 식별자 우선, 보조 공간 매칭 다음, 이름 유사도는 마지막 순서다.
- **품질 검사:** 전국 합계뿐 아니라 지역·유형별로 검사한다.
- **게시:** 데이터를 가리키는 manifest와 상태를 일관되게 전환한다.
- **서비스 확인:** 고정 분석 영역에서 도형·집계·출처 표시가 정상인지 확인한다.

**급감·실패 감지**

기존 30% 급감 거부는 최종 안전장치로 유지하되 다음을 추가한다.

| 검사항목 | 처리 |
|---|---|
| 응답에 행이 있는데 파싱 결과 0건 | 실패 |
| 전국 합계는 정상이나 특정 시도·유형이 통째로 사라짐 | 게시 보류 |
| 좌표·높이·용도·준공일 채움률 급락 | 이전 배포본과 비교해 경고·보류 |
| 페이지 상한 도달·`totalCount` 불일치 | 불완전 수집으로 처리 |
| 정상적으로 0건인 지역 | 완전 수집 근거와 함께 0건 인정 |
| 취소·폐업·철거로 인한 실제 감소 | 변화 근거 검토 후 게시 가능 |
| 최초 적재부터 일부 지역 누락 | 이전 건수가 없어도 커버리지 검사로 차단 |

전국 단위 전체 실패를 피하려고 지역별 정상본을 유지할 수는 있다. 이 경우 결과는 **지역별 기준일이 다른 혼합 스냅샷**임을 표시한다.

**실거래 수집량 예시 [추정]**

시군구 250개, 6개 서비스, 최근 2개월, 평균 1.5페이지라면:

`250 × 6 × 2 × 1.5 = 하루 약 4,500회`

24개월 최초 적재는 같은 가정으로 약 54,000회다. 실제 시군구 목록·서비스별 쿼터·최대 페이지 크기로 다시 산정하고 며칠에 나눠 수집한다.

늦은 신고·정정·해제를 반영하려면 최근 2개월만 영구적으로 갱신해서는 안 된다. 과거 월도 순환 재수집한다. 고유 거래 ID가 없는 서비스에서는 동일 금액·면적·일자의 실제 복수 거래를 단순 해시 중복 제거로 지우지 않도록 **월별 원본 집합을 보존하고 교체**한다.

**모니터링**

초기에는 로그와 SQLite 상태표로 충분하다.

- 마지막 시도·성공·자료 기준일
- 지역별 적재 완료율과 미해결 연결 건수
- API 호출량·429·인증 실패·재시도
- 디스크 여유·프로세스 RSS·적재 시간
- 데이터별 유효기간 초과 여부

화면 배지와 별도로 실패 알림 경로를 마련한다. 여기서는 알림을 발송하거나 설정하지 않았다.

**6. 시뮬레이션 데이터와 연산 위치**

**공통 장면 데이터**

3D·일조·바람·UTCI가 같은 `scene`을 사용해야 한다.

`분석 영역 + 주변 영향 영역 + 건물 도형·높이 + 지형 + 수목 가정 + 사용자 편집 + 좌표 원점 + 버전`

높이는 `대장/공간자료 수치`, `층수 기반 추정`, `사용자 입력`, `미상`을 구별한다. 층수에 임의 층고를 곱한 값을 측정 높이처럼 표시하지 않는다.

| 기능 | 필수 입력 | 권고 연산 위치 | 핵심 조건 |
|---|---|---|---|
| 3D 매스 | 건물 도형·높이, 지형, 지역 좌표 원점 | 서버 범위 추출＋브라우저 생성·표시 | 미상 높이는 기본적으로 풋프린트로 표시 |
| 일조·그림자 | 날짜·시간대·태양위치·건물·지형 | 브라우저 Worker/GPU, 반복 결과 캐시 | 사용자 편집 변경 시 재계산 |
| 일조시간 지도 | 수광면·시간 간격·주변 차폐물 | 브라우저 또는 단일 계산 워커 | 결과 격자와 시간 해상도 명시 |
| 바람장미 | 관측/EPW 풍향·풍속·기간·품질 플래그 | 사전 집계＋브라우저 차트 | 무풍·결측 처리와 관측소 정보 표시 |
| 바람 시뮬레이션 | 매스·지형·유입풍·조도·계산영역·격자 | 브라우저 탐색 계산 또는 별도 워커 | 장미와 CFD 결과를 구별 |
| UTCI | 기온·습도·풍속·평균복사온도 | 복사장·바람장 생성 후 Worker 계산 | 기상·형상·모델 가정의 품질 전파 |

**일조**

기하학적 일조시간에는 실시간 날씨 API가 필요하지 않다. 구름을 반영한 실제 일사량과 구별한다.

분석 반경 밖 건물도 그림자를 드리울 수 있으므로 화면에 보이는 원만 잘라 계산하지 않는다. 태양고도와 최대 건물 높이를 고려해 주변 영향 영역을 추가한다. 낮은 태양고도에서 영향 범위를 제한했다면 결과에 기록한다.

**바람 CFD의 현실성**

**일반적인 3D CFD를 Next 요청 안에서 Lightsail 한 대로 처리하는 것은 권고하지 않는다.**

D3Q19 LBM의 분포함수 두 벌을 float32로 저장한다고만 가정해도:

- `256 × 256 × 64 × 19 × 4 × 2` ≈ **0.64GB**
- `512 × 512 × 128 × 19 × 4 × 2` ≈ **5.10GB**

이는 도형·속도장·경계조건·렌더링 메모리를 제외한 계산치다. 공간 해상도를 높이면 시간 단계 부담도 증가한다.

권고 대안은 다음 두 경로다.

| 경로 | 용도 | 구현 방향 |
|---|---|---|
| 브라우저 탐색 시뮬레이션 | 바람 방향·차폐·상대적인 흐름 이해 | WebGPU 지원·메모리 예산 확인, 제한된 영역·격자, 결과에 모델 수준 표시 |
| 별도 3D 계산 | 검증된 CFD 결과 생성 | 로컬 GPU PC 또는 필요할 때만 켜는 워커, 작업 동시성 1부터 시작 |

간이 2D·준3D 흐름을 구현했다는 이유로 “LES CFD와 동등”하다고 표시해서는 안 된다. 3D CFD를 제품 완료 조건에 포함한다면 별도 solver 검증이 필요하다.

작업 상태는 SQLite에 저장하고 워커가 가져간다. 임대시간·재시도·취소만 지원하면 되며 Redis·분산 큐는 초기 필수가 아니다.

Lightsail은 일반적인 소형 플랜에서 CPU 버스트 용량을 사용하므로 지속적인 계산 부하에도 불리하다. [AWS CPU 성능 안내](https://docs.aws.amazon.com/lightsail/latest/userguide/baseline-cpu-performance.html)

**UTCI**

UTCI의 어려운 부분은 최종 수식보다 **평균복사온도와 국지 바람의 산정**이다.

- EPW 기온·습도만으로 공간별 UTCI 지도가 완성되지 않는다.
- 일사·그늘·하늘가시율·장파복사·지표 반사와 수목 가정을 정의해야 한다.
- 공식 근사식은 10m 높이 풍속을 입력으로 하며 풍속 적용 범위를 0.5~17m/s로 안내한다. 보행 높이 CFD 풍속을 그대로 넣지 않고 변환·적용 방법을 명시해야 한다.
- 적용 범위 밖 값을 조용히 잘라 정상 결과처럼 표시하지 않는다. [UTCI 공식 계산기](https://utci.org/utci_calc.php)

EPW/TMYx는 대표적인 기후연도이지 오늘의 날씨가 아니다. 관측소·거리·고도차·자료 기간·대표연도 여부를 표시한다.

**3D·DXF 내보내기**

- **GLB:** 브라우저에서 동일 장면을 내보낸다.
- **3DM:** `rhino3dm.js`/WASM을 후보로 삼는다. 브라우저와 Node 지원이 공식 안내돼 있다. 닫힌 솔리드·레이어·단위는 샘플 파일로 검증해야 한다. [Rhino3dm 문서](https://developer.rhino3d.com/guides/opennurbs/what-is-rhino3dmio/)
- **SKP:** 공식 Desktop SDK의 사용권·배포 조건을 확인한 Windows/macOS 변환 경로를 먼저 검증한다. Linux 서버에서 바로 생성된다고 가정하지 않는다. 초기에는 로컬 Windows 워커가 작업을 받아 SKP를 생성하는 구성이 가능하다. [SketchUp 개발자센터](https://developer.sketchup.com/)
- **DXF:** 분석 원본 도형을 사용한다. 단위·투영좌표계·지역 원점·레이어명을 기록한다.
- 모든 형식에서 원점·축 방향·높이 기준·도형 ID를 유지한다. 시각적 높이 과장은 기본 실척 내보내기에 반영하지 않는다.

**7. 서버 용량 산정**

**현재 사양에 대한 판단**

[확인] 7월 프로젝트 문서에는 **Lightsail 1GB**로 기록돼 있다. 현재 운영 인스턴스가 여전히 같은 사양인지는 미확인이다. [기존 사양 기록](/D:/V-coding/16-SiteAnalysis/docs/superpowers/specs/2026-07-12-improvement-roadmap-design.md:10)

1GB가 현재 사양이라면 전국 건물·필지 조회, 기존 앱과 신형 앱 병행, 이미지·PPT 처리를 안정적으로 함께 운영하는 목표에는 부족하다고 판단한다. 서버 전체 동거 프로세스까지 확인해야 최종 증설 폭을 결정할 수 있다.

**디스크 [추정]**

앞의 소스별 최대치를 단순 합산하지 않는다. 대장 원본 중 운영에 필요 없는 필드와 GIS 중복 속성은 가공 후 제외한다.

| 구성 | 활성 자료 예상 |
|---|---:|
| 건물·필지·토지이용·행정경계 | 25~65GB |
| 실거래 24개월·개발·공급 자료 | 4~12GB |
| 학교·학구·상가·인구·OSM | 3~10GB |
| 광역 지형·선정 기상 자료 | 2~7GB |
| 표시용 타일·집계 산출물 | 3~10GB |
| **활성 데이터 합계** | **약 40~105GB** |
| 분석·내보내기·허용된 영상 캐시 | 10~30GB |
| 앱·로그·운영 여유 | 15~25GB |

정밀 5m DEM 전국본은 위 합계에 기본 포함하지 않는다. 확보·허용 여부와 실제 크기에 따라 추가한다.

데이터 볼륨 크기는 다음 조건으로 결정한다.

`활성 자료 + 보존할 이전 파일 + 새 배포 staging + 작업 여유 ≤ 볼륨의 75%`

예를 들어 활성 60GB, 이전 변경 파일 40GB, 새 staging 40GB, 캐시·여유 30GB이면 170GB로 256GB 볼륨 안에서 운영할 수 있다. 반대로 전국 core가 커져 이 조건을 넘으면 512GB가 필요하다.

**RAM·CPU [추정]**

| 용도 | 예산 |
|---|---:|
| OS·프록시·PM2 | 0.5~1GB |
| 기존·신형 Next 런타임 | 1~2GB |
| DB·파일 캐시 | 2~3GB |
| 제한된 공간 계산·내보내기 작업 | 1~2GB |
| 권고 서버 | **8GB RAM, 2vCPU부터** |
| 로컬 전국 가공 PC | 32GB RAM 권장, SSD 작업 여유 200~400GB |

전국 도형을 한 번에 JS 배열로 읽지 않는다. 범위 조회·청크 처리·메모리 상한을 사용한다. `better-sqlite3`의 동기 질의와 무거운 공간 연산이 웹 이벤트 루프를 오래 점유하지 않도록 계산 작업을 Worker나 별도 프로세스로 제한한다.

**모든 타일의 PPT 계약**

타일에는 최소한 다음이 들어간다.

`입력 조건 / 데이터 버전 / 결과 상태 / 출처 목록 / 기준일 목록 / 미확인·추정 내역 / 렌더링 설정`

PPT 생성 중 새 데이터를 조회하지 않는다. 화면과 PPT가 같은 결과를 사용하며, 출처는 해당 슬라이드 하단에 보인다. 시뮬레이션의 카메라·시각·계절·격자도 슬라이드 조건에 포함한다.

미완료 타일은 성공한 빈 그림으로 변환하지 않는다. 내보낼 경우 ‘계산 미완료’, ‘자료 없음’, ‘미확인’을 구별한다. 조판·레이어 스택은 포함된 타일의 출처와 제한을 상속한다.

**현재 의존성 상태 [확인]**

`better-sqlite3`, Turf, `proj4`, `shapefile`, `pptxgenjs`는 직접 의존성으로 선언돼 있다. `three`, `rhino3dm`, `pmtiles`, `flatgeobuf`, `geotiff`는 직접 의존성 선언이 없다. GDAL·osmium·타일 생성기·CFD 도구의 설치 여부는 확인하지 않았다. 이번 작업에서 설치하지 않았다.

**10. A 데이터 기반 구축 단계**

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| **A0. 취득·권리·규모 검증** | 공간파일 이용조건, 학구도 도형, 높이 필드, 지형, 기상, SKP 경로 검증. 도시·농촌·산지·도서 샘플 가공 | 원천별 취득 가능 여부·권리·실제 크기·채움률·블로커가 확정됨 |
| **A1. 공통 데이터 계약** | 사용자 DB 분리, `source_release`·실행 이력·manifest·타일 결과 계약, 좌표·식별자 규칙 | 한 분석의 화면·PPT·내보내기가 같은 버전을 가리킴 |

| **A3. 전국 공간 기반** | GIS건물·대장·필지·지가·용도지역·계획시설·격자·학구·DEM | 전국 커버리지 명세와 지역별 누락 표시, R*Tree 성능 확인 |
| **A4. 27종 도판과 내보내기 기반** | 정적 도판·구성비·레이어 스택·조판·DXF, 공통 출처 계약. 일조·바람장미 입력 연결 | 모든 타일이 PPT 계약을 가지며 화면·수치·보고서가 일치 |

A0의 대표 지역 샘플은 전국 범위를 축소하는 것이 아니라 **전국 적재 방식과 비용을 결정하기 위한 검증**이다.

전체 완료 판정에는 다음을 포함한다.

- 시군구 경계를 넘는 반경에서도 실거래·학교·사업이 누락되지 않는다.
- 동일 입력·동일 버전으로 다시 계산한 집계가 일치한다.
- 신규 배포가 실패해도 이전 정상 데이터가 유지된다.
- 원천 장애를 정상 0건으로 표시하지 않는다.
- 도판 27종과 추가 타일 모두에 출처·기준일·미확인 상태가 있다.
- PPT·DXF·3D가 같은 객체·단위·조건을 사용한다.
- 브라우저 GPU 미지원·계산 취소·워커 재시작을 처리한다.
- 전국 자료 실측 후 디스크 여유와 콜드 응답 목표를 검증한다.

이 보고서의 성능·용량은 설계 목표이며 실측 결과가 아니다. 다음 실행의 첫 산출물은 **원천별 권리·취득·크기·채움률을 확인한 A0 검증표**가 되어야 한다.
