## 1. 현재 API 인벤토리

### 1-1. 분석 1회(`/api/poi-search` + `/api/rail-network`)의 호출 흐름

`src/lib/data-provider.ts:243` 클라이언트는 `poi-search`(NDJSON 스트림)와 `rail-network`를 병렬로 부릅니다. 서버 `src/app/api/poi-search/route.ts:265-392`는 `park`, `maintenance`, `osm`, `residential`(+`planned`)의 4개 태스크를 `collectSourcesInParallel`로 동시에 수집합니다. 그다음 `attachRecentTrades`(RTMS)와 `crossCheckMaintenanceCompletion`을 **순차로** 실행합니다(`route.ts:401-410`). 공통 캐시는 `poi-cache.ts`로, SQLite `poi_source_cache` 테이블에 (source, 격자 lat/lng, radius) 키로 7일 TTL을 적용합니다. 실패하면 만료된 캐시로 대체하고 stale 표시를 붙입니다.

## 5. 최적화 제안

### 5-1. 원칙: "요청 경로는 로컬 DB만 읽는다"
재구축의 목표 상태는 다음과 같습니다.
- 분석 1회의 외부 호출은 **대상지 필지 조회(VWorld 1~3회) + 선택적으로 주소 검색 1회**뿐입니다.
- 나머지는 전부 배치로 적재한 전국 테이블을 공간 질의로 읽습니다.
- 현재의 read-through 구조는 "전국 파일이 없는 소스"에만 남깁니다.

| 계층 | 소스 | 주기 |
|---|---|---|
| **L0 정적·수동** | 정비구역 SHP(VWorld 수동), 예정 철도 레지스트리, 학구도 | 60일 / 수시 / 연 |
| **L1 전국 파일 배치** | 건축물대장(총괄·표제부), GIS건물통합정보, 연속지적도·용도지역, 법정동 경계, 학교, 상가, 버스정류장, 공원, SGIS 격자, OSM PBF, 입주예정 | 월 / 분기 / 연 |
| **L2 전국 API 배치** | 청약홈(일), RTMS 전 유형(일, 최근 2개월만 갱신), 정비 통합·표준(주), 서울·부산·경기 정비(일), K-APT(월), R-ONE(주), 주택인허가(월) | cron + flock(현행 유지) |
| **L3 실시간** | 대상지 PNU·용도지역·공시지가, 주소 검색, (선택) TMAP 경로 | 요청 시, SQLite 캐시 |

### 5-2. 공간 인덱스
- better-sqlite3에는 **R*Tree 모듈이 기본 포함**되어 있습니다. 모든 POI 테이블에 `(minX,maxX,minY,maxY)` rtree를 붙이면 bbox 1차 필터 뒤 haversine으로 정밀 필터를 할 수 있습니다. 지금의 `queryDatasetInBbox`를 일반화하면 됩니다.
- 폴리곤(정비구역, 학구도, 법정동, 용도지역)도 rtree로 후보를 추린 뒤 JS에서 point-in-polygon 또는 교차 판정을 합니다. PostGIS는 지금 규모에서는 과합니다. 전국 필지(약 3,900만) 수준까지 가면 그때 검토합니다.
- 법정동 판별: 반경 원과 법정동 폴리곤의 교차로 대체하면 **역지오코딩 21회가 0회**가 되고 샘플링 누락도 사라집니다.

### 5-3. 사전 계산 격자 (선택, P1)
- 250m 격자(서울 생활인구가 전환하는 국가표준격자와 동일)마다 "가장 가까운 역·초등학교·버스정류장 거리, 1km 내 상가 수, 인구" 같은 값을 **야간 배치로 사전 계산**합니다.
- 점수 엔진(`analysis-engine.ts`)은 격자를 조회하고 반경만 보정합니다. 그러면 점수가 결정적이고 지역 간 비교(백분위)가 가능해집니다.

### 5-4. 캐시 계층 정리
- **L1 메모리**(프로세스): 스냅샷 파일, 코드 테이블.
- **L2 SQLite 소스 캐시**(`poi_source_cache`): 적재 전환 뒤에는 "결과 캐시"로만 씁니다. 주의할 점: 지역 단위 소스(서울, 부산)를 좌표 키로 캐시하는 문제(§2)를 고칩니다.
- **L3 적재 테이블**: `ingest_run`의 신뢰 표시와 급감 거부 규칙을 모든 배치에 적용합니다.
- 격자 키: 현재 반경별 소수 자릿수 방식은 좋습니다. 적재 전환 뒤에는 결과 캐시 TTL을 소스 갱신 주기에 맞춰 무효화합니다(적재 성공 시 해당 source 행 삭제).

### 5-5. 호출 절감·지연 개선 (재구축 전이라도 바로 할 수 있는 것)
1. Overpass POI 쿼리에서 `building=*` 3줄을 제거합니다(`overpass-api.ts:64-67`). 응답이 크게 줄고 429 확률도 낮아집니다.
2. 서울·부산 정비 원천의 `resolveSource` 키를 (source, 시도)로 바꿉니다(`maintenance-project-search.ts:268-275`).
3. RTMS를 반경과 교차하는 모든 LAWD_CD로 확장합니다. 법정동 목록에서 시군구 코드를 뽑으면 되므로 추가 역지오코딩이 필요 없습니다.
4. RTMS와 교차검증 단계는 현재 병렬 수집이 끝난 뒤에 순차로 돕니다. 주거 태스크 안으로 옮기면 정비 태스크와 겹쳐 돌 수 있습니다.
5. `.env.example`의 `NCP_MAP_CLIENT_ID/SECRET`를 코드와 같은 `NCP_CLIENT_ID/SECRET`로 맞춥니다. `GG_OPEN_API_KEY`, `APPLYHOME_API_KEY`, `NAVER_CLIENT_*`, `OVERPASS_URL`도 누락되어 있습니다.
6. 공공 API 전부에 `_type`이나 포맷을 명시하고 "행이 있는데 0개를 파싱하면 예외"를 거는 원칙을 모든 신규 원천에 계약으로 적용합니다. 현재는 대장과 정비에만 있습니다.

### 5-6. 레이트리밋·비용
- data.go.kr: 개발계정 평균 일 1,000회, 운영계정은 활용사례를 등록하면 최대 일 10만 회 수준입니다([이용가이드](https://www.data.go.kr/ugs/selectPublicDataUseGuideView.do)). RTMS는 개발 단계에서도 일 10,000회입니다. **배치 전환 시 운영계정 신청**이 필요합니다.
- 키 하나(`DATA_GO_KR_API_KEY`)를 모든 서비스가 공유합니다. 서비스별 트래픽은 따로 집계되지만, 키가 노출되면 전부 교체해야 합니다(2026-07-22 노출 이력). 배치용과 런타임용 키를 분리하는 것을 권장합니다.
- 비용: 위 계획은 전부 무료 원천입니다. 유료 가능성은 NCP Maps 무료량 초과와 TMAP(월 220만 원 정액 또는 종량제)뿐입니다.

### 5-7. 신뢰성
- 조용한 스키마 변경(XML→JSON, 봉투 제거, camelCase)은 **배치에서 더 위험합니다**. 적재 후 **골든 샘플 검증**(역삼동 오피스텔 N건 이상, 다산동 공동주택 56건 등 고정 지점 기대치)을 cron 끝에 추가합니다.
- 배치 실패 알림: `ingest-cron.sh` 로그에만 남습니다. 실패 시 알림(메일이나 웹훅)과 화면 배지(이미 있음)를 이중으로 둡니다.
- 대용량 가공(표제부, PBF, 격자)은 Lightsail 메모리 부담이 큽니다. **로컬에서 빌드한 뒤 SQLite 파일을 배포**합니다(현재 `git archive`와 공유 링크 구조와 호환).
