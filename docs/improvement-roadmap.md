# 16-SiteAnalysis 완성도 개선 로드맵

작성일: 2026-07-31
출처: Claude 분석 10건 + Codex(GPT-5.6, reasoning high) 분석 10건 = 20건
모든 항목은 실제 코드 확인을 거쳤다. 파일:라인은 작성 시점 기준.

## 원칙

1. **안전망 먼저.** 검증·롤백 장치 없이 정확성 리팩터를 하면 회귀를 배포로 발견하게 된다.
2. **뿌리부터.** 증상(오탐 1건)이 아니라 원인(단지 식별 키 부재)을 고친다.
3. **모르는 것은 모른다고 표시.** 데이터 공백을 조용히 "없음"으로 렌더링하지 않는다. 보고서가 의사결정에 쓰이므로 이 원칙이 기능 추가보다 우선한다.
4. 각 단계는 독립 배포 가능해야 한다. 단계 끝마다 `lint + test:maintenance + build` 통과가 완료 조건.

## Phase 0 — 안전망 (선행 필수)

이후 모든 작업의 전제. 다른 Phase보다 먼저 끝내야 한다.

### 0-1. 원자적 릴리스 + 헬스체크 + 롤백 `[L]`
- **현재**: `deploy/deploy.sh:51-98`이 운영 디렉터리에 직접 압축을 풀고 그 자리에서 빌드한 뒤 PM2 프로세스를 `delete` 후 재생성한다. 헬스체크도 롤백도 없다.
- **위험**: 빌드가 중간에 실패하면 운영 디렉터리가 반쯤 덮인 상태로 남고 서비스가 죽는다. 2026-07-31 배포가 두 차례 무산된 경험이 있어 실제 노출된 위험이다.
- **제안**: `releases/<타임스탬프>/`에 풀고 그 안에서 `lint → test → test:maintenance → build`를 모두 통과시킨 뒤 `current` 심볼릭 링크를 교체, `pm2 reload` 후 HTTP 헬스체크. 실패 시 링크를 이전 릴리스로 되돌린다. 릴리스 3개 보관.
- **효과**: 데이터 계약 회귀나 기동 실패가 서비스 중단으로 이어지지 않는다.

### 0-2. CI 파이프라인 `[S]`
- **현재**: `.github/workflows` 없음. 테스트 18종과 타입체크가 전부 수동이다. 더구나 기본 `test` 스크립트(`package.json:18`)에 `test:maintenance`가 빠져 있어, 정비사업·실거래 계약 테스트는 별도로 부르지 않으면 안 돈다.
- **제안**: push/PR에서 `lint + test + test:maintenance + build` 실행. 동시에 `test` 스크립트가 `test:maintenance`를 포함하도록 정리한다.
- **효과**: 배포 직전에야 문제를 발견하는 패턴이 사라진다. 0-1의 릴리스 게이트와 같은 명령을 공유한다.

## Phase 1 — 데이터 정확성의 뿌리

지도·보고서에 나가는 숫자의 신뢰도를 결정하는 층. 서로 얽혀 있어 한 번에 다루는 편이 효율적이다.

### 1-1. 단지 식별을 복합 키로 전환 `[M]` (Codex #4 + Claude #1 통합)
- **현재**: `residential-search.ts:290`이 `bldNm`에서 "동" 접미사만 뗀 문자열로 중복 제거한다. 같은 반경의 서로 다른 "주공아파트"·"현대아파트"가 하나로 합쳐질 수 있다. 같은 뿌리에서 `apt-enrichment.ts`의 이름 부분 매칭이 오탐을 낸다 — 2026-07-31 라이브에서 "개포자이르네"가 "개포자이"(212세대)로 잘못 결합된 것을 확인했다.
- **제안**: 단지 식별 키를 `법정동코드 + 본번 + 부번`(+ 좌표 근접)으로 바꾼다. 이름은 동점 처리·표시용으로 강등. 실제 동일 단지의 동별 건물만 병합한다. RTMS는 이미 구조화 지번(`umdCd`/`bonbun`/`bubun`)을 주므로 브리지가 자연스럽다.
- **효과**: 단지 수·세대수·K-APT 보강 대상·지도 마커의 누락과 오병합이 함께 해소된다.

### 1-2. 법정동 탐색을 공간 기반으로 교체 `[L]`
- **현재**: `residential-search.ts:97-127`이 중심과 8방향 9개 점만 역지오코딩해 법정동을 찾는다. 경도 오프셋에 위도와 같은 `radiusM / 111000`을 써서, 서울 위도에서 동서 실거리가 의도한 반경보다 짧다.
- **제안**: 최소 조치로 경도에 `cos(위도)` 보정을 넣고, 정식으로는 법정동 경계 폴리곤과 원을 교차시킨다. 적응형 격자 샘플링이 중간 대안.
- **효과**: 반경 안 주거단지가 법정동 누락 때문에 통째로 빠지는 사례가 줄어든다. 1-1보다 뒤에 두는 이유는, 탐색 범위를 넓히면 중복 제거 결함이 더 크게 드러나기 때문이다.

### 1-3. 캐시 키 좌표 정합성 `[M]`
- **현재**: `poi-cache.ts:27`과 `data-provider.ts:128`이 좌표를 `toFixed(4)`로 키화한다. 서울 기준 같은 키 안에서 약 14m 편차가 생겨, 최소 반경 100m 조회에서 경계 POI가 다른 위치의 결과로 재사용될 수 있다.
- **제안**: 반경보다 충분히 작은 공간 격자로 키를 만들되, 반환 시 실제 좌표 기준 거리 필터를 다시 적용한다.
- **효과**: "반경 내" 판정이 주소 미세 이동에 따라 흔들리지 않는다.

## Phase 2 — 응답성

첫 검색이 10초 이상 걸리는 문제의 앞뒤를 함께 다룬다.

### 2-1. 독립 원천 병렬 수집 `[M]`
- **현재**: `poi-search/route.ts:191-302`가 공원 → 정비사업 → OSM → 주거 → 예정주거 → RTMS를 순차로 기다린다. 실제로 앞선 결과에 의존하는 것은 RTMS와 준공 교차검증뿐이다.
- **제안**: 독립 원천을 `Promise.allSettled`로 병렬화하고, RTMS 결합과 교차검증만 후속 단계로 남긴다.
- **효과**: 총 소요가 "원천별 합계"에서 "가장 느린 원천"으로 내려간다.

### 2-2. RTMS 수집 완결성과 타임아웃 `[M]`
- **현재**: `rtms-trades.ts:14-18, 91-111`이 월 최대 3페이지(3,000건)만 읽고 절단 사실을 남기지 않는다. 6개월을 순차 호출하며 개별 fetch에 timeout이 없다.
- **제안**: `totalCount` 기준으로 필요한 페이지를 제한 동시성으로 모두 가져오고, 상한을 넘기면 `partial` 상태와 누락 범위를 노출한다. 요청 timeout과 취소 신호를 적용한다.
- **효과**: 거래량 많은 시군구에서 최근가·최고가·건수가 조용히 과소 집계되지 않는다.

### 2-3. 요청 취소 전파 `[M]`
- **현재**: `site-analysis-app.tsx:92-125`의 `cancelled` 플래그는 상태 반영만 막는다. `data-provider.ts:63-72, 122-177`의 HTTP 요청에 `AbortSignal`이 없어 이전 지역 작업이 서버에서 계속 돈다.
- **제안**: effect마다 `AbortController`를 만들어 fetch까지 전파하고, 취소 오류를 실패 상태로 바꾸지 않는다.
- **효과**: 주소를 연속으로 바꿀 때 외부 API 낭비와 SQLite 경합이 줄고, 오래된 응답이 최신 결과를 덮는 경쟁이 사라진다.

### 2-4. 수집 진행 상황 표시 `[M]`
- **현재**: 첫 검색 10초 이상 동안 화면에 단계 정보가 없다.
- **제안**: 원천별 완료를 스트리밍해 "지하철 완료 · 아파트 수집 중"처럼 보여준다. 2-1의 병렬화와 같은 구조 변경에 얹는다.
- **효과**: 체감 대기가 줄고, 특정 원천이 느릴 때 사용자가 원인을 안다.

## Phase 3 — 신뢰 표시 (모르는 것을 모른다고 말하기)

기능 추가가 아니라 이미 가진 데이터의 한계를 드러내는 작업. 보고서가 외부에 전달되므로 우선순위가 높다.

- **현재**: `poi-cache.ts:6, 69-92`가 7일 TTL이 지난 데이터도 원천 실패 시 `status: "cached"`로 반환하고, `source-status-text.ts:30-35`는 "수집일"로만 표기한다.

- **효과**: 오래된 정비 단계나 거래 요약을 최신으로 오인하지 않는다.

### 3-2. 보고서 본문의 결측 표기 `[M]`

- **효과**: "없음"과 "수집하지 못함"이 구분된다. 이 로드맵에서 의사결정 안전성에 가장 직접적인 항목.

### 3-3. 원천 실패 메시지 사용자 언어화 `[S]`

## Phase 5 — 구조 정리

동작은 같지만 이후 변경 비용을 좌우한다.

### 5-1. 보고서 슬라이드 계약 고정 `[M]`
- **현재**: `ppt-canvas-renderer.ts:2362-2435`, `ppt-generator.ts:2665-2673`이 주거 POI 7개당 슬라이드를 동적으로 추가한다. 기본 14장 + 주거 페이지 수라서 결과에 따라 장수가 달라진다. "23슬라이드"는 특정 조건의 결과일 뿐 계약이 아니다.
- **제안**: 주거 섹션을 고정 페이지 수로 예약하고, 부족분은 요약/빈 상태로, 초과분은 우선순위 + "외 N개"로 처리한다.
- **효과**: 목차·페이지 참조·검수 기준이 항상 같아진다.

### 5-2. PPT 생성기 중복 제거 `[L]`
- **현재**: `ppt-generator.ts`(2,700줄)와 `ppt-canvas-renderer.ts`(2,495줄)가 "수치 parity 유지" 주석을 달고 같은 레이아웃을 두 벌 구현한다. 2026-07-30 실거래 컬럼 추가 때도 양쪽을 동일하게 고쳐야 했다.
- **제안**: 레이아웃 상수와 행 빌더를 공용 모듈로 분리하고, 두 렌더러는 그리기 백엔드만 담당하게 한다.
- **효과**: parity 어긋남 계열 버그가 구조적으로 사라진다. 5-1을 먼저 하면 이 작업의 대상이 명확해진다.

## 순서 요약

```
Phase 0 (안전망)     → 0-1 원자적 배포, 0-2 CI
Phase 1 (정확성)     → 1-1 단지 식별 키, 1-2 법정동 탐색, 1-3 캐시 좌표
Phase 2 (응답성)     → 2-1 병렬화, 2-2 RTMS 완결성, 2-3 취소 전파, 2-4 진행 표시
Phase 3 (신뢰 표시)  → 3-1 stale, 3-2 결측 표기, 3-3 메시지, 3-4 배지, 3-5 신선도, 3-6 각주
Phase 4 (커버리지)   → 4-1 경기도, 4-2 실거래 상세
Phase 5 (구조)       → 5-1 슬라이드 계약, 5-2 렌더러 통합
```

Phase 3은 대부분 S 난이도라 Phase 1·2 사이에 끼워 넣어도 된다. 다만 3-1(stale)은 3-6(각주)의 선행이고, 3-2와 3-3은 같은 매핑 테이블을 공유하므로 묶어서 한다.
